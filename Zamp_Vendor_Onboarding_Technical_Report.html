1. Executive Summary & Design Tenets

Modern procurement teams process dozens of vendor onboarding packets quarterly. Traditional manual workflows suffer from high operational latency, lack of auditable logs, and acute vulnerability to Business Email Compromise (BEC) and third-party payment redirection.

This application replaces that manual burden with an end-to-end autonomous ingestion pipeline. A submission is evaluated against 7 discrete verification layers, yielding an instantaneous classification (APPROVED, PENDING, or REJECTED), a 0–100 Composite Risk Score, and a guardrailed vendor communication dispatch.

3. Mathematical Checksum Engines

Unlike naive systems that rely on basic regex length checks, this platform re-implements national mathematical checksum algorithms to catch data-entry typos and transpositions:

  • Indian GSTIN (Luhn-variant Mod-36 Algorithm): The engine independently re-calculates the 15th check character over the first 14 characters using alternating weighting ($1, 2$) across base-36 characters. It extracts the 2-digit state code (verifying against 38 valid Indian tax states, e.g., 36 → Telangana, 27 → Maharashtra) and isolates the embedded PAN.
  • United States ABA Routing Checksum: Verifies the 9-digit FedWire routing number via the weighted algorithm: $$(3d_1 + 7d_2 + 1d_3 + 3d_4 + 7d_5 + 1d_6 + 3d_7 + 7d_8 + 1d_9) \pmod{10} = 0$$
  • IRS Employer Identification Number (EIN) Prefix Verification: Cross-checks the first two digits against the official ~80 valid IRS campus prefixes, rejecting invalid prefixes such as 07 or 17.
  • European & UAE IBAN Checksum (ISO 7064 / Mod-97): Converts alphanumeric country codes and BBAN into integers and checks $(N \pmod{97} = 1)$ to detect single-digit transpositions in 22–23 character strings.

4. Offline Semantic Bank Directory (Zero 3rd-Party API Dependencies)

Live banking validation APIs (such as Penny-Drop or Confirmation-of-Payee) require enterprise KYC and incurring per-call fees. To make the application fully self-contained and resilient against network outages, the engine embeds an offline directory of 40+ major banking institutions:

  • Indian IFSC Prefixes (first 4 characters): Resolves SBIN → State Bank of India, HDFC → HDFC Bank, ICIC → ICICI Bank, UTIB → Axis Bank, PUNB → Punjab National Bank, BARB → Bank of Baroda, CNRB → Canara Bank, UBIN, IOBA, KKBK, YESB, etc.
  • US ABA Routing Prefixes (first 4 digits): Resolves 0210 → JPMorgan Chase, 0260 → Bank of America, 0710 → Wells Fargo, 0740 → PNC Bank, 0440 → HSBC, etc.
  • International SWIFT/BIC Codes: Resolves DBSSSGSG → DBS Bank (Singapore), INGDDEFF → ING Bank (Germany), DEUTDEFF → Deutsche Bank, BARCGB22 → Barclays (UK).
Semantic Cross-Verification in Action: If a vendor enters "HDFC Bank" in the bank name field but provides an IFSC code starting with SBIN..., the engine detects that SBIN resolves to State Bank of India and flags a Bank Name Semantic Mismatch for manual review.

5. Entity Resolution & Mule Account Detection

String equality checks fail in enterprise procurement because commercial entities frequently write variations of legal abbreviations (e.g., Pvt Ltd vs Private Limited).

The Stage 4 Payee Name Matching engine applies a 3-step normalization algorithm:

  1. Legal Suffix Pruning: Removes 24 common international corporate identifiers: private, pvt, limited, ltd, llc, llp, inc, corp, gmbh, ag, pte, plc, sarl, bv, etc.
  2. Punctuation & Case Normalization: Strips special characters, standardizes ampersands (& → and), and trims whitespace.
  3. Dual Sequence Matching: Runs comparative fuzzy similarity on both standard order and alphabetically-sorted tokens (preventing failures on inverted naming like "Cloud Apex" vs "Apex Cloud").

Operational Boundary: An account holder name differing completely from the registered entity (e.g., registered entity Brightpath Consulting LLC with account holder Sunrise Trading Co, similarity < 20%) is stopped immediately as a Third-Party Mule Account Pattern.

6. Business Email Compromise (BEC) & Fraud Defense

Payment redirection via Business Email Compromise accounts for over \$2.7 billion in annual enterprise fraud losses. In Edge Case 3 (Orion Industrial Supplies), an active vendor's tax ID matches ERP records, but an incoming submission requests routing to a new IBAN and originates from a look-alike domain (orion-industrial.co instead of orion-industrial.de).

The engine counters this attack vector with deliberate architectural choices:

  • State Preservation: The request is classified as PENDING + Manual Review (rather than hard-rejected, since genuine suppliers do legitimately migrate banking partners).
  • Out-of-Band Callback Protocol: Payment enablement is locked pending a mandatory phone verification to the verified telephone number already recorded on file in the ERP.
  • Security Contact Routing (Critical Feature): The automated system notification is deliberately routed to the registered contact on file, NOT the submitter. If an attacker has compromised an external rep's mailbox or spoofed a submission, sending confirmation to the submitter would hand the attacker control of the verification channel.
  • No Internal Fraud Disclosure: Watchlist hits and fraud alarms trigger neutral decline notices. Telling a threat actor which internal heuristic caught them provides training feedback on how to evade controls in subsequent attempts.

7. Composite Risk Scoring Methodology

Every submission receives an automated 0–100 Composite Risk Score displayed on a color-graded visual gauge. This provides procurement and finance operations with instant triaging capability:

Signal / Heuristic Points Added Operational Rationale
Watchlist Hit (Account / Tax / Entity) +50 pts Direct match against confirmed fraud accounts or debarred suppliers.
Bank Account Change on Existing Vendor +25 pts High velocity payment redirection indicator (primary BEC vector).
Look-Alike Email Domain Anomaly +20 pts Domain differs from ERP vendor master record.
Payee Name Mismatch (Mule Account) +20 pts Account holder diverges from registered corporate entity.
Bank Country Mismatch (Offshore) +15 pts Settlement jurisdiction outside country of incorporation.
Each Unresolved Field / Fix Item +10 pts Vendor clerical error, missing document, or tax format typo.
Free Mailbox Domain (Gmail / Yahoo) +5 pts Advisory signal indicating absence of enterprise email infrastructure.

Risk Tiers: Low (0–20): Direct straight-through ERP creation; Medium (21–45): Minor vendor fix required; High (46–70): Multi-signal escalation to Fraud Ops; Critical (71–100): Hard block.

8. Differential Resubmission Engine (Delta Tracking)

When an incomplete or flagged application is resubmitted (e.g., Edge Case 4b, where a vendor corrects their email and uploads bank proof but re-submits the identical invalid EIN), the engine executes a differential comparison against the preceding run in SQLite.

The dashboard highlights the exact delta across three categories:

  • Resolved Items cleared since last submission (e.g., Contact Email Provided, Bank Proof Attached).
  • Still Open Items that persist uncorrected (e.g., US EIN Prefix Invalid).
  • New Issues Anomalies introduced in the latest iteration.

9. Guardrailed LLM Communication & Graceful Degradation

The application utilizes an LLM (Gemini 1.5 Flash) strictly for human communication drafting, governed by four fail-safe guardrails:

  1. Data Isolation: Internal risk labels, watchlist match reasons, and internal security notes are completely excluded from the payload supplied to the model.
  2. Forbidden Keyword Sanitizer: Model responses are scanned for sensitive terms (watchlist, fraud, suspicious, sanction, mule, risk score, compromise). If detected, the response is rejected.
  3. Account Number Redaction: Prevents disclosure of unmasked account numbers in outbound text.
  4. Deterministic Template Fallback: If the API key is absent, the model encounters a network error, rate limit, or fails output sanitization, the pipeline falls back seamlessly to deterministic, polite email templates. The core workflow never crashes.

10. Production Roadmap & System Boundaries

A transparent evaluation acknowledges current prototype boundaries and defines the path to enterprise production:

  • Live Government Registries: Currently validates mathematical checksums and prefix tables. Production would connect to live API endpoints: GSTN (India), IRS TIN Matching (US), VIES (EU), and ACRA (Singapore).
  • Confirmation of Payee / Penny Drop: Account ownership is validated via algorithmic entity resolution. Production would integrate real-time penny-drop verification (RazorpayX, Cashfree) or Confirmation-of-Payee (UK/EU).
  • Document Understanding: Currently tracks document presence via checklists. Next iteration incorporates an OCR/vision pipeline to extract text from tax certificates and compare directly with submitted form values.
  • Durable Infrastructure: SQLite ephemeral store on Community Cloud would transition to PostgreSQL/Supabase with audit logging and Webhook dispatch to ERPs (NetSuite, SAP, Workday).
